# FCCVisualization 1.0.0 release report

Prepared on the `release/1.0` branch (2026-10-15). Not tagged, not published:
tagging and publishing are left to the maintainer.

## Environment

Ubuntu 24.04 container (2 cores, 7 GB), GCC 13.3 (all configurations below),
Clang 18 (core configuration), CMake 3.28, Ninja, Catch2 3.4.0, Python 3.13,
Doxygen 1.9.8, Sphinx. Third-party packages built from source: ROOT 6.38.06,
DD4hep v01-38, podio v01-08, EDM4hep v01-01-01, CED 1.10 (glced, test only);
pybind11 2.13.6; Node.js 22 with Playwright and phoenix-event-display 4.2.3
(test only). See `docs/DEPENDENCIES.md`.

Notes on the run:

- The first full run found one failure, `docs::stdlib_filters` in
  `only-RASTER`: `data::Point::position` was not initialised, so a
  default-constructed point had an indeterminate position (valgrind:
  uninitialised value in `stdlib::Cone::Criterion`). Fixed (zero
  initialisation, also `SeriesInfo::entries`) with a regression test in
  `tests/stdlib/test_shape_filters.cc`. `only-RASTER`, `only-CED` (its first
  build had caught a half-edited test file), `only-DD4HEP` and
  `only-EDM4HEP` were rerun after the fix; `all` and `static` were built
  after it. The rows above are the final results.
- The `all` configuration's `docs` target failed in the first run only
  because this report did not exist yet; rebuilt afterwards in the same
  build directory: Doxygen (undocumented public symbols fail) and Sphinx
  with `-W` pass with no warnings.
- ROOT tests needing X run under Xvfb (Mesa llvmpipe); REve and Phoenix
  viewer tests run in headless Chromium.
- Running the CLD tests found three problems, fixed after the matrix run
  (the `all` build and the DD4hep tests were rerun, 36/36 pass): CTest
  replaced the caller's `LD_LIBRARY_PATH` for the DD4hep tests, so detector
  drivers outside DD4hep were not found (now prepended with
  `ENVIRONMENT_MODIFICATION`); a sub-detector cut by `max_volumes` was
  registered without a word in the report (now reported as incomplete, with
  a test); one imported test assumed the first CLD sub-detector has a
  primitive solid (it is an assembly; the test now takes the first
  sub-detector with one). The full CLD detector has 324328 volumes, above
  the default `max_volumes` of 200000 (documented on the adapter page).
  `only-DD4HEP`, `all` and `static` were rerun after these fixes (the table
  shows those runs; the `static` rerun had glced off `PATH`, so `ced::glced`
  was not registered and one test more, the new detector test, was).

## Open decisions

1. Adapter registration style: kept as implemented (adapters register by
   name, chosen explicitly with `load <adapter> <path>`; lookup by file
   extension takes the first match in name order, so `.root` goes to
   `detector` before `edm4hep`). Listed here for the maintainer's
   confirmation.
2. ROOT backend order, 3. undo/redo scope, 4. Python binding: resolved (see
   `STATUS.md`).

## Unverified items

- ROOT TEve: interaction tested by driving the TEve calls that mouse actions
  end in, under Xvfb; real mouse input on a physical display and remote X
  were not exercised.
- Phoenix: the output was loaded into the Phoenix event-display library in
  headless Chromium; the Phoenix web application (its UI) was not run.
- The real CLD detector was loaded with drivers built from k4geo sources
  against DD4hep without Geant4 (`tools/k4geo_cld`), not with a Key4hep
  installation.
- Platforms other than Linux, compilers other than GCC 13 and Clang 18, and
  dependency versions other than those listed: untested.
